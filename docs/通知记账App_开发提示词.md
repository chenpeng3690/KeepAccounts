=== 提示词开始 ===

你是一名资深 Android 工程师，请为我从零开发一个**纯本地、离线运行的通知自动记账 App**。这是一个个人自用工具，不需要登录、不需要服务器、没有任何联网行为。

请严格按照以下规格实现。遇到规格未覆盖的细节，按「简单、可靠、对小白友好」的原则自行决定并在 README 中说明，不要反复向我提问。

## 0. 硬性约束（不可妥协）

1. **零联网**：AndroidManifest 中**不声明** `INTERNET` 权限，不引入任何网络库、埋点 SDK、崩溃上报 SDK、广告 SDK。App 完全离线可用。这条是整个产品的核心卖点，也是我选择它的原因。
2. **数据只存在本机**：不使用任何云同步。数据安全通过「本地备份 + 导入」保障。
3. **用户是小白**：任何界面都不允许出现正则表达式、DSL 语法、JSON、代码。解析规则必须用「点选 / 勾选 / 填词」的方式配置。
4. **自动化的东西必须可关**：自动备份、自动记账、自动清理都要有明确开关和默认值，默认行为必须保守（默认关闭或默认观察模式）。
5. **不允许静默丢数据**：解析失败、字段缺失、规则冲突时，宁可进入「待确认箱」让用户判断，也不要直接丢弃。

## 2. 通知捕获与系统集成

### 2.1 核心能力
通过 `NotificationListenerService` 读取通知。需要在 `AndroidManifest.xml` 注册：

```xml
<service
    android:name=".service.NotiListenerService"
    android:exported="false"
    android:permission="android.permission.BIND_NOTIFICATION_LISTENER_SERVICE">
    <intent-filter>
        <action android:name="android.service.notification.NotificationListenerService" />
    </intent-filter>
</service>
```

### 2.2 必须处理的真实问题
- **授权引导页**：首次启动必须有一个清晰的引导页，说明为什么需要「通知使用权」，提供「去开启」按钮跳转 `Settings.ACTION_NOTIFICATION_LISTENER_SETTINGS`，并实时显示当前是否已授权（`NotificationManagerCompat.getEnabledListenerPackages()`）。未授权时**账单首页顶部显示醒目红色横条**「通知读取已关闭，记账已停止 · 去开启」——这个状态必须常驻可见，不能只藏在设置里，因为服务被系统杀掉后 App 会静默失效，用户可能好几天才发现。
- **两个通知权限要分清**：读取通知只需「通知使用权」；**发送**记账反馈通知需要 `POST_NOTIFICATIONS`（Android 13+）。两者独立，不要混为一谈，也不要因为拿到前者就以为能发通知。
- **国产 ROM 保活提示**：小米 / 华为 / 荣耀 / OPPO / vivo 上要提示用户开启「自启动」「后台运行白名单」「电池优化豁免」，给出**按品牌定制的分步图文说明**，并提供跳转到对应系统设置页的按钮（`Intent` 带品牌对应的 Action，失败则跳应用详情页）。
- **通知折叠/摘要**：处理 `FLAG_GROUP_SUMMARY` 的组摘要通知，避免重复解析；优先解析子通知。同一 `key` 的通知更新要按「更新」而非「新增」处理。
- **取全文本**：正文要拼接 `EXTRA_TITLE`、`EXTRA_TEXT`、`EXTRA_BIG_TEXT`、`EXTRA_SUB_TEXT`、`EXTRA_INFO_TEXT`，用换行分隔，不要只取 `EXTRA_TEXT`。
- **通知被清空**：可选能力，用户关闭通知后仍保留已解析的原始文本（我们存的是文本副本，不依赖通知存活）。

### 2.3 白名单
- 白名单按**应用包名**管理，只有白名单内的应用通知才会进入解析流程，其他一律忽略（连原始文本都不落库）。
- 内置默认白名单：**微信**（`com.tencent.mm`）、**支付宝**（`com.eg.android.AlipayGphone`），默认开启。
- 白名单管理页：列出设备已安装应用（`PackageManager` 查询 + 显示图标和名称），支持搜索、开关。可以「从已安装应用添加」，也要支持「手动输入包名添加」（针对找不到的应用）。
- **通用规则开关**：白名单页顶部有一个独立的「通用兜底规则」总开关（默认开启）。开启后，白名单内**没有专属规则**的应用通知会走通用规则；关闭后则只处理有专属规则的应用。
- 白名单变更后立即生效，不需要重启服务。

## 3. 数据模型

请设计以下表（字段名可优化，语义必须保留）：

**`notification_raw`（原始通知）**
`id, packageName, appLabel, title, text, postedAt, receivedAt, groupKey, ruleId(nullable), matchResult(enum: MATCHED/PENDING/REJECTED), rejectReason`

**`rule`（解析规则）**
`id, name, packageName(nullable=通用规则), priority, isBuiltin, state(OBSERVING/ACTIVE/DISABLED), templateJson, directionWords, excludeKeywords, defaultAccountId, defaultCategoryId, amountHint, stats(hits/confirmed/rejected/lastHitAt), createdAt, updatedAt`

**`txn`（账单）**
`id, type(EXPENSE/INCOME/TRANSFER), amount(以「分」为单位存 Long，禁用 Double), accountId, toAccountId(nullable), categoryId, merchant, note, occurredAt, createdAt, updatedAt, source(MANUAL/NOTIFICATION/IMPORT/TEMPLATE/ADJUSTMENT), ruleId, rawNotificationId, status(NORMAL/PENDING), deletedAt(nullable), deleteReason, editCount`

**`txn_edit_log`（账单编辑历史）**
`id, txnId, beforeJson, afterJson, editedAt` —— 用于编辑后回溯（个人使用，保留最近 20 条即可）

**`account`（账户）**
`id, name, type(CASH/DEBIT/CREDIT/BNPL/LOAN/INVESTMENT/OTHER), initialBalance(分), currentBalance(分), creditLimit(分, nullable), billDay, repayDay, includeInNetWorth(Boolean), icon, colorHex, sortOrder, archived, createdAt`

**`category`（分类）**
`id, name, type(EXPENSE/INCOME), icon, parentId(nullable), sortOrder, isBuiltin`

**`budget`（预算）**
`id, scope(TOTAL/CATEGORY), categoryId, period(MONTH/YEAR), amount, startDate`

**`backup_record`（备份记录）**
`id, filePath, createdAt, sizeBytes, encrypted, txnCount, accountCount, schemaVersion, type(MANUAL/AUTO)`

**金额一律用 Long 存「分」**，展示时格式化，杜绝浮点误差。

## 4. 解析引擎（本产品的核心，请重点实现）

### 4.1 处理流水线

```
通知到达
 ① 白名单校验（包名不在白名单 → 直接丢弃，不落库）
 ② 规则路由（该包名的专属规则按 priority 排序；无专属规则 → 通用规则）
 ③ 噪音前置过滤（快速否决，见 4.4）
 ④ 模板匹配 + 字段抽取（金额 / 商户 / 方向 / 时间）
 ⑤ 语义校验（金额合理性、方向可判定性、时间合理性）
 ⑥ 去重（见 4.6）
⑦ 特殊场景分流（退款冲销 / 转账双边 / 待确认）
⑧ 写库 + 账户余额更新（同一事务）
⑨ 记录原始通知 + 规则命中统计 + 规则健康度检查
⑩ 结果反馈（浮悬提示，见 4.9）
```

每一步都要有日志可查（「解析日志」页面，用户可看到每条通知为什么被记账 / 被过滤 / 进了待确认）。

### 4.2 规则模型：不用正则的「片段模板」

规则的内部表示是**有序片段列表**，每个片段是以下两种之一：

- `literal`：固定文案，例如 `"支付成功"`
- `slot`：可变槽位，类型为 `amount` / `merchant` / `time` / `direction` / `account`，可带约束（长度上限、货币单位前后缀）

匹配模式：
- `ordered_contains`（默认，推荐）：片段按顺序在文本中依次出现即可，允许片段之间有任意无关内容；
- `fuzzy`：开启后忽略空白、全半角、标点、emoji、大小写差异，并允许 1~2 个字的差异容忍度（用编辑距离或 token 覆盖率打分，阈值 ~0.82）。

用户永远看不到这个结构。**引擎内部可以把它编译成正则或状态机，但绝不向用户展示语法**；如果自动生成了内部正则，必须先用用户提供的样例验证通过才允许保存。

示例（用户视角看到的是原文的高亮，不是这个 JSON）：
```
微信支付 · 向你付款 [商户] [金额]元
```

### 4.3 小白友好的规则创建流程（关键交互，请严格照此设计）

入口：`设置 → 解析规则 → 新建规则`

**步骤 1｜选应用**
从已安装应用列表选择，或选择「通用规则（兜底）」。显示应用图标 + 名称。

**步骤 2｜贴样例**
大文本框：「把手机上收到的那条通知原文粘贴进来」。
支持「从最近通知里挑一条」——列出最近 7 天白名单应用收到的通知（来自 `notification_raw`），点一下就自动填入，免去复制粘贴。这一步非常重要，请务必实现。
可再贴 1 条同类通知（可选），用于自动学习「哪些部分是变化的」。

**步骤 3｜点选字段**
系统把原文渲染成可点击的文本块：
- 自动识别出所有数字、货币符号（`¥ ￥ 元 块 RMB`）、常见分隔符，做成可点选的高亮块；
- 用户点哪个数字 → 指定为「金额」；
- 用户拖选一段文字 → 指定为「商户/对方」（系统会自动把这段里与第二条样例不同的部分判定为可变槽位）；
- 如果找不到可点选的内容，提供「手动划词」：用户长按选择文本再点「设为商户」。

**步骤 4｜确认收支方向（自动预测 + 一键确认）**
系统用内置方向词表预测，以药丸按钮展示「支出 / 收入」两个选项，默认选中预测项，用户可以改。
内置支出词：支付、付款、消费、扣款、转出、支出、已付、已扣、付款成功、缴费
内置收入词：收款、到账、收入、退款、转入、已收、入账、红包到账、返现
冲突时（同时出现「退款」和「支付」）以**收入/退款优先**。

**步骤 5｜设定默认值**
选择「记到哪个账户」「默认分类」。这两个可以在通知解析不出来时兜底。

**步骤 6｜忽略词（系统推荐，勾选即可）**
系统根据该应用通知的历史文本，自动推荐 3~8 个高频噪音词（如「优惠券」「活动」「红包」「限时」「直播」），以可勾选的标签展示，默认全选。用户可以自己再加词。
这一屏要有说明文案：「含这些词的通知不会记账」。

**步骤 7｜测试验证**
提供输入框，预填刚才的样例，再加 2 条测试用例（用户可自己改）。点「测试」后逐条显示：
- ✅ 匹配 / ❌ 不匹配
- 抽取结果：金额 25.00 元 · 商户「瑞幸咖啡」· 方向 支出
- 不匹配时提示最可能的原因（例如「未找到金额」「缺少固定文案片段『支付成功』」）
任何一条 ❌ 都不允许保存，但可以「返回调整」。这个测试是强制的，防止用户配出永远匹配不上的规则。

**步骤 8｜保存为「观察模式」**
保存后规则默认处于 **OBSERVING（观察模式）**：命中的通知会记录到「解析日志」并标记为「待确认」，**不自动生成账单**。
在解析日志里，用户可以对一条命中记录点「确认正确」或「判为噪音」。
- 累计 3 条「确认正确」且无「判为噪音」→ 页面提示「这条规则看起来可以了，是否启用自动记账？」→ 用户点一下 → ACTIVE。
- 出现 2 条「判为噪音」→ 提示「规则可能不准，建议调整」。

规则列表页每条规则显示：应用图标、名称、状态徽章（观察中 / 已启用 / 已停用）、近 7 天命中数、上次命中时间。
支持：编辑（走同一流程，进入时预填）、复制、停用、删除、调整优先级（上下移动）。

### 4.4 噪音过滤（多层，必须全部实现）

这是记账准确率的关键。必须按以下顺序逐层否决，任一层命中即拦截，并在解析日志中记录**被哪一层拦截**：

**L0 通知类型层**：通知 `category` 为 `CATEGORY_PROMO` / `CATEGORY_RECOMMENDATION` / `CATEGORY_SOCIAL` / `CATEGORY_SYSTEM`（服务类除外）→ 拦截。

**L1 全局噪音词库（用户可编辑）**：
内置：`活动 / 优惠 / 大促 / 满减 / 满__减__ / 红包 / 优惠券 / 券 / 抽奖 / 积分 / 会员 / 限时 / 秒杀 / 拼团 / 直播 / 开播 / 上新 / 推荐 / 猜你喜欢 / 签到 / 邀请 / 返现福利 / 即将过期 / 领取 / 预约 / 订阅 / 版本更新 / 升级 / 运费券 / 津贴 / 省钱卡 / 百亿补贴 / 领券 / 下单立减 / 首单 / 新人 / 试用 / 关注 / 转发`
规则：命中即拦截（但**同时存在明确支付成功语义词时可以豁免**，见 L4 豁免逻辑）。

**L2 规则级排除词**：该规则自己的 `excludeKeywords`。

**L3 结构性否决**：
- 文本中没有任何数字 → 拦截（记「无数字」）
- 数字存在但不构成金额形态（既无货币符号前后缀，又无「元/块/¥」，且是日期、单号、手机号、百分比、数量）→ 拦截
- 金额 ≤ 0，或金额 > 规则设定的单笔上限（默认 100000 元）→ 拦截
- 文本长度过短（< 4 字）或为空 → 拦截

**L4 方向否决 / 豁免**：
- 明确命中支付成功语义（如「支付成功」「付款成功」「已支付」「扣款成功」「到账」）→ **豁免 L1 噪音词**（防止「支付成功，已为你节省 5 元优惠券」这类被误杀）
- 既无收入词也无支出词 → 不直接记账，进入**待确认箱**（可配置为「直接丢弃」，默认进待确认）

**L5 观察模式**（见 4.3 步骤 8）：新规则不直接记账。

**L6 去重窗口**：同包名 + 同金额 + 同商户在 **60 秒**内只生成 1 条账单（通知更新、重复推送）。可用 `交易单号` 时以单号 hash 做全局去重（跨导入/通知）。

**L7 规则健康度**：某规则连续 7 天命中数为 0 且之前有稳定命中 → 在规则页打黄色警示「可能已失效，通知格式可能变了，请重新取一条样例更新规则」。这是应对微信/支付宝改版的关键机制。

### 4.5 内置规则（必须开箱可用）

请内置以下规则，标记 `isBuiltin=true`（不可删除，可停用、可编辑）：

**微信支付**（`com.tencent.mm`）
覆盖这些常见形态（用片段模板，不要写死全等匹配）：
- `微信支付` + `支付成功` / `已支付` + `¥/￥金额` + 商户
- `微信支付凭证`
- `收款到账` / `微信支付收款` + 金额（→ 收入）
- `转账` + 金额（→ 支出或收入按方向词）
- `退款到账` + 金额（→ 收入，并尝试冲销原支出）
- 商户名通常在标题行或正文末行，做多位置尝试抽取

**支付宝**（`com.eg.android.AlipayGphone`）
- `支付成功` / `付款成功` / `你已成功付款` + 金额 + `元`
- `收款成功` / `到账`（→ 收入）
- `余额宝收益` / `收益到账`（→ 收入，分类为「投资收益」）
- `花呗` / `还款成功`（→ 转账：储蓄卡 → 花呗账户）
- `退款成功`（→ 收入/冲销）
- 金额常为 `12.50元` 无空格形式，注意数字与「元」粘连的抽取

内置规则的默认分类猜测：正文含「外卖/餐饮/咖啡/奶茶」→ 餐饮；「打车/地铁/公交/加油」→ 交通；「话费/流量/宽带」→ 通讯；「电费/水费/燃气/物业」→ 居住；「电影/演出/游戏」→ 娱乐；「药/医院/挂号」→ 医疗；「超市/便利店/生鲜」→ 日用。用关键词表打分取最高分，低于阈值则留空让用户选。

### 4.6 通用兜底规则

- 只在「通用规则开关」开启时生效；
- 逻辑：从文本中提取**第一个带货币符号或「元/块」单位的金额**作为金额；用方向词表判定收支；商户取「支付成功」等关键词之后的剩余文本（去除标点，截断 30 字）；
- **通用规则命中的一律进入「待确认箱」**，绝不直接入账（因为置信度低）；
- 用户可以在待确认箱里对某条记录「一键采纳」，并可选择「以后这个应用都这样记」→ 自动把该应用的通知样本转成一条专属规则草稿（预填好片段和字段），用户确认后保存。这条「从待确认升级为专属规则」的路径必须实现，它是小白用户建立规则的捷径。

### 4.7 待确认箱（独立底部 Tab）

待确认箱是**底部导航的独立一级页面**（不是首页提示条），因为它是自动记账准确率的安全网，需要常驻可达。

展示所有 `status=PENDING` 的记录，卡片形式显示：应用图标、原文摘要、抽取结果（金额/商户/方向，可点击就地修改）、来源（哪条规则 / 通用兜底 / 观察模式）。
操作：`确认入账` / `修改后入账` / `判为噪音` / `批量确认`。
顶部右侧提供「管理规则」入口，直达规则列表（避免为了配规则绕到设置里）。
底部 Tab 图标上显示数量角标；数量为 0 时不显示角标（角标不做零点）。

**空态设计（重要，不要做成空白页）**：待确认为 0 时，页面下半部分直接展示「最近 7 天解析概况」——用大字号显示 `已自动入账 42 条 / 已拦截 18 条噪音 / 待确认 0 条`，下方接一段**被拦截通知的摘要列表**（数据复用 `notification_raw` 中 `matchResult=REJECTED` 的记录，含拦截原因）。
这让这个 Tab 永远有内容可看，同时把「解析日志」的入口也安放在这里：列表底部一个「查看全部解析日志」，点击进入完整日志页。
**用户不需要为了查日志先进设置**。

### 4.8 退款、转账、还款、特殊场景

- **退款**：识别到「退款」语义且金额匹配到 60 天内的一笔同金额同商户支出 → 提示「检测到这可能是 X 月 X 日那笔的退款」，默认**冲销原账单**（原账单标记 `refunded`，或在原账单上减记），而不是新增一笔收入。找不到匹配 → 按收入记账，分类「退款」。
- **转账**：同一通知里出现两个账户标识，或规则明确标记为转账 → 生成一条 `TRANSFER` 记录，扣减源账户、增加目标账户，**不计入收支统计**。
- **信用卡还款 / 花呗还款**：金额匹配到某信用卡账户的欠款 → 记为「转账：储蓄卡 → 信用卡」，计入负债减少，不计入支出。
- 所有自动判定都要在账单详情里显示「系统判断依据」，用户可一键改类型。

### 4.9 记账结果反馈（浮悬提示）

**目标**：用户付款时人在微信 / 支付宝里，不在本 App 内，所以「应用内弹提示」是看不到的。必须能在别的 App 上层看到「刚刚记了一笔」。

**技术方案（请按此实现，不要申请悬浮窗权限）**
用**系统通知 + heads-up 横幅**实现。Android 的原生横幅（heads-up notification）本身就是浮在屏幕顶部的提示，不需要 `SYSTEM_ALERT_WINDOW`，也不需要引导用户去开一堆危险的系统权限。

- 独立通知渠道：`channelId = "ledger_feedback"`，`IMPORTANCE_HIGH`（才会浮横幅），声音设为静默、不震动（记账反馈不该像来电一样吵）。
- 需要 `POST_NOTIFICATIONS` 权限（Android 13+），在首次启用该功能时请求；被拒绝时功能自动降级为「不提示」并在设置页说明原因，不要反复弹权限框。
- **前台判断**：如果通知到达时本 App 正在前台，不推系统通知，改用应用内 Snackbar（避免同一件事提示两次）。

**三种反馈形态**

1. **自动入账成功**
   标题：`已记账 ¥25.00`
   正文：`瑞幸咖啡(国贸店) · 餐饮 · 微信零钱`
   附一个 Action 按钮「撤销」（点击直接软删除这笔账单，进回收站）。
   点击通知本体 → 打开该笔账单详情。

2. **待确认**
   标题：`有一笔待确认 ¥30.00`
   正文：`抖音 · 商户未识别，点一下确认`
   附一个 Action 按钮「确认入账」（不解锁 App 直接入账）。
   点击通知本体 → 打开待确认箱。

3. **被噪音规则拦截** → **不发任何提示**（这是纪律，不要为了"让你知道我在工作"而打扰）。

**防打扰规则**
- **合并**：同一应用或同一账户在 60 秒内产生多条账单时，合并成一条：`已记账 3 笔，共 ¥88.00`，点击展开列表。避免连续支付时通知刷屏。
- **静音时段**：设置里可配置一个时间段（默认 23:00–07:00），期间不弹横幅，只静默投递到通知栏。
- **总开关**：设置 →「记账提示」，三档：`全部提示（默认）` / `仅成功入账` / `不提示`。切换后立即生效，不需要重启服务。
- 用户手动记账时**不触发**浮悬提示（是他自己记的，不需要再告诉他一遍）。

**注意**：反馈通知的文案要短。横幅在锁屏 / 其他 App 上停留约 3–4 秒，正文超过一行就会被截断，金额和商户名必须出现在前 12 个字内。

## 6. 回收站

- 删除账单 = 软删除，写入 `deletedAt`，账单从列表消失。

- 操作：`恢复`（回到原日期位置，账户余额重算；若原账户已归档则提示选择其他账户）、`立即彻底删除`（二次确认）、`清空回收站`（二次确认，需输入「清空」二字确认）。
- 恢复后要弹出轻提示，提供「撤销」入口（5 秒内）。
- 若删除的是 `TRANSFER`，恢复时两端账户一起回滚。

## 7. 账户管理（重点）

- 账户类型：现金、储蓄卡、信用卡、花呗/白条（BNPL）、借呗/网贷（LOAN）、投资账户、其他。
- 每个账户：名称、类型、初始余额、当前余额、图标、颜色、是否计入净资产、备注、归档。
- **余额计算规则（必须严格按此实现）**：
  - `当前余额 = 初始余额 + Σ(该账户的收入) - Σ(该账户的支出)`（不含已删除账单，不含 `TRANSFER` 的两端重复计算）
  - `TRANSFER`：源账户减、目标账户加
  - **信用卡 / 花呗 / 网贷：余额以负数表示欠款**（例如 -3500 表示欠 3500），用户输入时用「欠款」正数输入，内部存负数，展示时显示「欠款 ¥3,500」
  - `净资产 = Σ(计入净资产的账户余额)`，负债账户的负余额天然相减
  - `总资产 = Σ(余额 > 0 的账户)`，`总负债 = Σ(余额 < 0 的账户的绝对值)`
- 信用卡额外字段：额度、账单日、还款日。展示「已用额度 / 可用额度」进度条，接近额度时变黄变红。
- 账户详情页：余额卡片、本月收入/支出、该账户全部流水（可按月筛选）、「校准余额」按钮。
- **校准余额**：用户输入实际余额，系统生成一条 `source=ADJUSTMENT` 的调整记录（差额，分类为「余额调整」），**不计入收支统计**，但在流水中可见。
- 资产总览页（可作为首页的一个 Tab 或卡片）：净资产大数字、总资产、总负债、资产构成环形图、近 30 天/12 个月净资产趋势折线、各账户列表（按余额排序）。
- 账户删除：若该账户下仍有未删除账单，**禁止删除**，提示「请先转移或删除该账户的 N 笔账单」，提供「一键转移到其他账户」。
- 账户排序支持拖拽。

## 8. 备份与导入导出

### 8.1 手动备份
- 一键备份，通过 SAF（`ACTION_CREATE_DOCUMENT`）让用户选保存位置，默认文件名 `NotiLedger-backup-yyyyMMdd-HHmmss.zip`。
- 备份包结构（zip）：
```
manifest.json      # schemaVersion, appVersion, createdAt, deviceModel, 各表行数, 每文件 SHA-256
data/accounts.csv
data/transactions.csv
data/categories.csv
data/rules.json    # 规则模板结构
data/budgets.csv
data/settings.json # 仅白名单/偏好，不含敏感
```
- 可选**密码加密**：勾选后输入密码，用 AES-256-GCM 加密整个 zip 流，密码用 PBKDF2 派生（迭代 ≥ 10 万次）。密码错误要给出明确提示而不是崩溃。
- 备份完成显示：文件大小、账单条数、账户数、耗时。

### 8.2 自动备份
- 设置项：`自动备份` 开关（**默认关闭**），周期选项：**1 天 / 3 天 / 7 天 / 30 天**（默认 7 天）。
- 位置：应用私有目录 `files/auto_backup/`（无需权限），并允许用户再指定一个外部目录做副本（通过 SAF 持久化 URI 授权 `takePersistableUriPermission`）。
- **保留份数**：默认 5 份，超出自动删最旧的（只删自动备份，不动手动备份）。
- 用 `PeriodicWorkRequest`，约束 `setRequiresBatteryNotLow(true)`，加 15~30 分钟 flex。设置页显示「上次自动备份时间」「下次预计时间」「当前占用空间」。
- 触发时机：即使周期未到，也可配置「每次 App 启动后若距上次备份超过周期则补一次」。
- 备份记录列表：时间、大小、类型（手动/自动）、能否恢复、删除。

### 8.3 恢复
- 选择备份文件 → 读取 `manifest.json` → **预览**：备份时间、账单数、账户数、应用版本、schemaVersion。
- 恢复模式三选一：
  1. `合并追加`（默认）：保留现有数据，按 ID + 内容 hash 去重后插入；
  2. `覆盖全部`（危险操作，二次确认 + 建议先自动备份当前数据）；
  3. `仅恢复规则与设置`。
- schemaVersion 不匹配时尝试自动迁移，失败则明确报错并保留原数据不动（**恢复必须在事务中，失败要完整回滚**）。

### 8.4 导入第三方账单（微信 / 支付宝）

这是必须做好的功能，因为用户首次使用时历史数据要靠它。

**通用能力**
- 导入页：选择文件（SAF，支持 csv / txt / zip）→ 自动识别来源（通过表头关键字嗅探，而不是依赖文件名）→ 字段映射预览 → 全量导入。
- **编码自动检测**：支付宝导出的 CSV 常为 **GBK/GB18030**，微信为 UTF-8。必须先探测（BOM / 尝试解码 + 中文比例启发式），探测失败允许用户手动切换编码。
- **跳过前导说明行**：支付宝 CSV 前若干行是说明文字和 `----` 分隔线，实际表头在中间。策略：逐行扫描，找到同时包含「交易时间」和「金额」的那一行作为表头，之前的内容忽略。
- 预览首批 20 行，显示「识别到：支付宝 / 共 1234 行 / 金额列 = 金额(元) / 收支列 = 收/支」。
- 金额清洗：去掉 `¥ ￥ , 空格`，处理 `-` 和括号负数写法，转为「分」。
- 时间解析：支持 `yyyy-MM-dd HH:mm:ss`、`yyyy/MM/dd HH:mm`、`yyyy年M月d日 HH:mm`。
- **状态过滤**：`交易关闭` / `已关闭` / `已退款` / `退款成功` / `等待付款` 等 → 默认跳过（可勾选「也导入」）。
- **去重**：优先用「交易单号 / 交易订单号」做 hash 唯一键；无单号时用 `(时间±1分钟 + 金额 + 交易对方)` 组合 hash。已存在则跳过并计入「重复跳过」。
- 分批事务写入，每批 1000 行，显示进度条。
- **导入报告**：成功 N 条 / 重复跳过 M 条 / 因状态跳过 K 条 / 失败 F 条（失败明细可导出为 CSV，含行号和原因）。
- 导入完成后提示「是否立即核对账户余额」。

**微信账单字段映射**
`交易时间 → occurredAt`｜`交易类型 → 备注`｜`交易对方 → merchant`｜`商品 → note`｜`收/支 → type`｜`金额(元) → amount`｜`支付方式 → account 匹配`｜`当前状态 → 过滤`｜`交易单号 → dedupeKey`
注意：`收/支` 为 `/` 表示「不计收支」（如零钱充值、理财转入转出）→ 映射为 `TRANSFER` 或标记「不计收支」，不要算进支出统计。

**支付宝账单字段映射**
`交易时间 → occurredAt`｜`交易分类 → 分类猜测`｜`交易对方 → merchant`｜`商品说明 → note`｜`收/支 → type`｜`金额 → amount`｜`收/付款方式 → account 匹配`｜`交易状态 → 过滤`｜`交易订单号 → dedupeKey`
同样处理 `收/支` 为 `/` 的情况（余额宝转入转出等）。

**账户自动匹配**：导入时按「支付方式/收付款方式」的文本，模糊匹配已有账户名（如「招商银行储蓄卡(1234)」→ 匹配含「招商」的储蓄卡账户）；匹配不上则提示用户批量指定。

**导出**：支持导出当前全部账单为 UTF-8 BOM 的 CSV（Excel 直接打开不乱码），列与微信格式尽量对齐，便于迁出。

## 10. UI / 交互要求

- Material 3，简洁克制，参考「小而美」的个人工具风格。桌面图标要有设计感。
- **配色约定**：支出用红色系，收入用绿色系（中国用户习惯，不要用欧美配色）。
- **底部导航固定 5 个 Tab，顺序必须是**：`账单` / `资产` / `待确认` / `统计` / `设置`。
  - 「待确认」在中间偏左的第三位，是刻意为之——它是校对入口，比统计更高频，要放在拇指自然落点上。
  - 待确认 Tab 的图标右上角有数量角标（Material 3 `BadgedBox`），数量为 0 时**不显示角标**。
  - 这个顺序不要因为「统计看起来应该挨着账单」而调整。
- **不使用右上角齿轮承载设置**：设置保持为第五个 Tab。低频不是把它藏起来的理由，因为设置里包含「通知使用权状态」这种需要随时可查的系统状态。
- 空状态要有引导文案和插图（可用简单的 Compose 绘制矢量图，不要引入大体积图片资源）。待确认 Tab 的空态按要求展示「最近 7 天解析概况 + 被拦截通知摘要」，见 4.7。
- 所有危险操作（清空回收站、覆盖恢复、删除账户、删除规则）都要二次确认，确认文案要说清后果。
- 所有耗时操作（导入、备份、恢复）都要有进度和可取消。
- 字体大小、无障碍描述（`contentDescription`）要齐全。
- 支持深色模式，颜色要在两套主题下都保证对比度。

## 11. 验收测试用例（请自查，逐条通过）

1. 未授权通知使用权时，首页有醒目提示，点击可跳到系统设置页；授权返回后状态实时更新。
2. 收到微信「支付成功 ¥25.00 瑞幸咖啡」类通知 → 自动生成 1 条支出账单，金额 2500 分，商户非空。
3. 收到「限时活动！满 100 减 20，速来抢购」类通知 → **不生成任何账单**，解析日志显示被 L1 噪音词拦截。
4. 收到「支付成功 ¥25.00，已为你节省 5 元优惠券」→ **正常入账**（验证 L4 豁免逻辑，不能被 L1 误杀）。
